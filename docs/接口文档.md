# 接口文档

本文档描述 SpringHere Gin Server 当前对外 HTTP 接口，供前端和调用方对接。实现细节以仓库代码为准。

本地默认地址：

```text
http://localhost:8080
```

业务 API 前缀：

```text
/api/v1
```

本地允许的前端 Origin：

```text
http://localhost:5173
```

建议开发环境通过 Vite 代理访问 `/api`，前端只使用相对路径：

```ts
// vite.config.ts
export default defineConfig({
    server: {
        proxy: {
            "/api": {
                target: "http://localhost:8080",
                changeOrigin: true,
            },
        },
    },
});
```

## 1. 接口一览

| 方法     | 路径                         | 认证                      |
|--------|----------------------------|-------------------------|
| GET    | `/healthz`                 | 无                       |
| GET    | `/readyz`                  | 无                       |
| GET    | `/api/v1/auth/captcha`     | 无                       |
| POST   | `/api/v1/auth/login`       | 无（需验证码）                 |
| POST   | `/api/v1/auth/refresh`     | Refresh Cookie + Origin |
| POST   | `/api/v1/auth/logout`      | Refresh Cookie + Origin |
| GET    | `/api/v1/auth/me`          | Bearer Access Token     |
| GET    | `/api/v1/users`            | Admin Access Token      |
| POST   | `/api/v1/users`            | Admin Access Token      |
| GET    | `/api/v1/users/:id`        | Admin Access Token      |
| PATCH  | `/api/v1/users/:id`        | Admin Access Token      |
| DELETE | `/api/v1/users/:id`        | Admin Access Token      |
| PATCH  | `/api/v1/users/:id/status` | Admin Access Token      |
| POST   | `/api/v1/users/:id/kick`   | Admin Access Token      |

`GET /healthz` 只表示进程存活。`GET /readyz` 会检查 PostgreSQL 和 Redis。登录页对接见 [5.1](#51-登录页对接)。

## 2. 统一响应

所有业务接口返回：

```ts
interface ApiResponse<T> {
    code: number;
    message: string;
    success: boolean;
    data: T;
}
```

成功：

```json
{
  "code": 0,
  "message": "success",
  "success": true,
  "data": {}
}
```

失败：

```json
{
  "code": 1000,
  "message": "authentication required",
  "reason": "UNAUTHORIZED",
  "success": false,
  "data": null
}
```

判断结果时先看 HTTP 状态码，再用 `reason` 做业务分支。不要只判断外层 `code`，普通业务错误的外层 `code` 都是 `1000`。健康检查成功时 `message` 为 `ok` 或 `ready`。

分页有两层 `data`：

```ts
interface PageData<T> {
    data: T[];
    total: number;
    page: number;
    pageSize: number;
}

type PageResponse<T> = ApiResponse<PageData<T>>;
```

```json
{
  "code": 0,
  "message": "success",
  "success": true,
  "data": {
    "data": [],
    "total": 0,
    "page": 1,
    "pageSize": 20
  }
}
```

## 3. 认证模型

登录必须先拿一次性图形验证码，再提交账号密码。验证码只用于登录，不是登录态的一部分；刷新、退出、当前用户都不需要验证码。

登录成功后的会话由两部分组成：

- Access Token：JWT，登录和刷新接口通过 JSON 返回，调用方放在内存中，请求头为 `Authorization: Bearer <token>`。
- Refresh Token：高熵随机值，只存在 HttpOnly Cookie 中，JavaScript 无法读取。

Access Token 包含用户 ID、登录 session ID 与唯一 `jti`。每次受保护请求都会校验 Redis 中的 `auth:v2:session:{sessionID}`，且
`jti` 必须等于该会话当前的 Access Token 标识。合法但 session 不存在、或已被轮换的 JWT 同样返回 401。Redis 不保存原始 Token。

Refresh Token 在 Redis 中只保存 SHA-256 digest，并用 `auth:v2:refresh:{digest}` 索引到 session。刷新时会同时轮换 Refresh
digest 与 Access `jti`，上一对 Token 立即失效。会话 TTL 等于首次登录时的 Refresh Token 有效期，刷新不会延长这个绝对到期时间。

涉及 Refresh Cookie 的请求必须携带 Cookie：

```ts
fetch(url, {credentials: "include"});
```

```ts
axios.defaults.withCredentials = true;
```

默认有效期：

```text
Access Token: 15 分钟
Refresh Session: 30 天
```

刷新成功后：

- 原 Refresh Token 立即失效
- 原 Access Token 的 `jti` 立即失效，即使 JWT 自身还未到期
- 会话不会延长首次登录建立的绝对有效期

前端应对 `/auth/refresh` 做单飞：同一时间只发一个刷新请求，其它 401 等待它完成后再用新 Access Token 重试一次。不要拦截
`/auth/captcha`、`/auth/login`、`/auth/refresh` 自身的错误再去刷新 Token。`POST /auth/login` 返回的 `401 INVALID_CREDENTIALS`
表示账号或密码错误，应刷新验证码并提示用户，不要当成会话过期。

页面刷新后 Access Token 会丢失，应先调用 `POST /api/v1/auth/refresh`，成功后再请求 `/api/v1/auth/me`。

以下操作会删除 Redis 登录态，现有 Access Token 和 Refresh Token 都会立即失效：

- 用户退出登录
- 管理员踢用户下线
- 管理员修改用户资料、角色或密码
- 管理员启用或禁用用户
- 管理员删除用户

## 4. 公共类型

```ts
type Role = "admin" | "user";

interface AuthUser {
    id: string;
    email: string;
    remark: string;
    role: Role;
}

interface User extends AuthUser {
    active: boolean;
    online: boolean;
    created_at: string;
    updated_at: string;
}

interface TokenData {
    access_token: string;
    token_type: "Bearer";
    expires_in: number;
    user: AuthUser;
}

interface CaptchaData {
    captcha_id: string;
    image: string;
    expires_in: number;
}

interface LoginCommand {
    email: string;
    password: string;
    captcha_id: string;
    captcha: string;
}
```

`created_at` 和 `updated_at` 是 RFC 3339 时间字符串。用户响应不包含密码或密码 Hash。`CaptchaData.image` 已是完整 Data URL，可直接赋给 `<img src>`，不要再拼 `data:image/png;base64,` 前缀。

`User.active` 和 `User.online` 不是同一个意思：

| 字段 | 含义 | 典型用途 |
|------|------|----------|
| `active` | 账号是否启用，存在 PostgreSQL | 停用后不能登录 |
| `online` | 当前是否还有未过期的 Redis 登录会话 | 列表展示在线、决定能否踢下线 |

`online: true` 表示 Refresh 会话还在，关了浏览器也算在线，不是「正在看页面」。退出、被踢、改密、停用或删除后为 `false`。登录 / 刷新 / `/auth/me` 返回的是 `AuthUser`，不含 `active`、`online`。

## 5. 认证接口

### 5.1 登录页对接

推荐流程：

1. 进入登录页立刻 `GET /api/v1/auth/captcha`，把 `data.image` 绑到图片，把 `data.captcha_id` 存在组件状态里，不要放 `localStorage`。
2. 用户点击图片或刷新按钮时，再拉一次验证码，并清空输入框。
3. 提交登录时带上邮箱、密码、当前 `captcha_id` 和用户输入的 `captcha`。登录请求必须 `credentials: "include"`，否则浏览器不会保存 Refresh Cookie。
4. 登录失败后立刻重新拉验证码，清空验证码输入；成功后把 `access_token` 放内存，按 `expires_in` 管理过期。
5. 可选：按 `expires_in`（默认 120 秒）到时自动换一张图。

```ts
async function loadCaptcha(): Promise<CaptchaData> {
    const res = await fetch("/api/v1/auth/captcha");
    const json: ApiResponse<CaptchaData> = await res.json();
    if (!res.ok || !json.success) {
        throw json;
    }
    return json.data;
}

async function login(body: LoginCommand): Promise<TokenData> {
    const res = await fetch("/api/v1/auth/login", {
        method: "POST",
        headers: {"Content-Type": "application/json"},
        credentials: "include",
        body: JSON.stringify(body),
    });
    const json: ApiResponse<TokenData> = await res.json();
    if (!res.ok || !json.success) {
        throw json;
    }
    return json.data;
}
```

```tsx
<img
    src={captcha.image}
    width={160}
    height={48}
    alt="captcha"
    onClick={refreshCaptcha}
/>
```

登录页错误处理：

| HTTP | `reason`              | 建议提示             | 刷新验证码 |
|---:|-----------------------|------------------|-------|
| 400 | `INVALID_REQUEST`     | 请填写完整登录信息        | 是     |
| 400 | `INVALID_CAPTCHA`     | 验证码错误或已过期        | 是     |
| 401 | `INVALID_CREDENTIALS` | 邮箱或密码错误          | 是     |
| 429 | `TOO_MANY_REQUESTS`   | 验证码获取太频繁，请稍后再试   | 稍后重试  |
| 503 | `SERVICE_UNAVAILABLE` | 服务暂不可用           | 否     |
| 500 | `INTERNAL_ERROR`      | 服务内部错误           | 否     |

`INVALID_CAPTCHA` 和 `INVALID_CREDENTIALS` 是不同错误：前者只说明验证码无效，后者说明账号或密码不对。登录一旦失败，都不要复用这次的 `captcha_id`，直接换新图再试。

### 5.2 获取验证码

```http
GET /api/v1/auth/captcha
```

无需认证，也不需要 Cookie。成功：`200 OK`，`data` 为 `CaptchaData`。

```json
{
  "code": 0,
  "message": "success",
  "success": true,
  "data": {
    "captcha_id": "<uuid>",
    "image": "data:image/png;base64,...",
    "expires_in": 120
  }
}
```

| 字段           | 说明 |
|--------------|------|
| `captcha_id` | UUID，登录时原样回传 |
| `image`      | PNG Data URL，默认约 160×48 |
| `expires_in` | 有效期秒数，默认 `120` |

默认 4 位字符，来自 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`（不含 `0` `1` `O` `I` 等易混字符）。大小写不敏感，前端可按 4 位限制输入长度，允许用户输入小写。

验证码一次性使用，提交登录后无论对错都会失效。同一 IP 默认每分钟最多拉取 20 次，超出返回 `429 TOO_MANY_REQUESTS`。

### 5.3 登录

```http
POST /api/v1/auth/login
Content-Type: application/json
```

```json
{
  "email": "admin@example.com",
  "password": "password123",
  "captcha_id": "<uuid>",
  "captcha": "ab12"
}
```

| 字段           | 必填 | 说明 |
|--------------|----|------|
| `email`      | 是  | 合法邮箱，服务端按小写匹配 |
| `password`   | 是  | 明文密码 |
| `captcha_id` | 是  | 来自 `/auth/captcha` 的 UUID |
| `captcha`    | 是  | 用户看到的 4 位字符，最长 16 |

成功：`200 OK`，`data` 为 `TokenData`。

```json
{
  "code": 0,
  "message": "success",
  "success": true,
  "data": {
    "access_token": "<jwt>",
    "token_type": "Bearer",
    "expires_in": 900,
    "user": {
      "id": "<uuid>",
      "email": "admin@example.com",
      "remark": "Admin",
      "role": "admin"
    }
  }
}
```

后端同时写入名为 `springhere_refresh` 的 HttpOnly Cookie。服务端先核销验证码，再校验账号密码：

- `email` / `password` 格式不合法，或 `captcha_id` / `captcha` 缺失、过长、ID 不是 UUID：`400 INVALID_REQUEST`
- 验证码错误、过期、已使用或不存在：`400 INVALID_CAPTCHA`
- 错误账号、错误密码、禁用用户：统一 `401 INVALID_CREDENTIALS`，不区分具体原因

登录成功后不要再复用这次的验证码。开发环境可将 `captcha.enabled` 设为 `false`，此时登录可不带验证码字段；生产环境必须开启。前端建议始终走验证码流程，不要为本地环境写两套提交逻辑。

### 5.4 刷新 Token

```http
POST /api/v1/auth/refresh
Cookie: springhere_refresh=<HttpOnly Cookie>
```

无请求体。成功返回 `200 OK`，`data` 与登录接口相同，同时覆盖 Refresh Cookie。

Refresh Token 缺失、过期、已轮换或 Session 被删除时返回 `401 UNAUTHORIZED`，并清除当前 Refresh Cookie。

### 5.5 退出登录

```http
POST /api/v1/auth/logout
Cookie: springhere_refresh=<HttpOnly Cookie>
```

无请求体，不要求 Bearer Token。成功返回：

```json
{
  "code": 0,
  "message": "logged out",
  "success": true,
  "data": null
}
```

会删除当前 Session 并清除 Refresh Cookie。调用方无论响应是否成功，都应清空本地 Access Token 和用户状态。

### 5.6 当前用户

```http
GET /api/v1/auth/me
Authorization: Bearer <access_token>
```

允许角色：`admin`、`user`。成功返回 `ApiResponse<AuthUser>`。

## 6. 用户管理

`/api/v1/users` 下的接口都要求 `admin` 角色。普通用户访问返回 `403 FORBIDDEN`。密码只保存 bcrypt
hash。修改资料、角色或密码、切换激活状态以及删除用户前，会先撤销该用户全部登录态。管理员不能删除、停用或修改自己的角色。

用户管理读写接口的 `data` 都是 `User`（或分页里的 `User[]`），都带 `online`。只有列表和详情会查 Redis 得到真实在线状态；创建、修改、启停成功后会话已被清掉或尚不存在，响应里 `online` 固定为 `false`。

### 6.1 用户列表

```http
GET /api/v1/users?page=1&page_size=20&email=example&role=user&active=true
Authorization: Bearer <access_token>
```

| 参数          | 必填 | 默认值  | 说明               |
|-------------|----|------|------------------|
| `page`      | 否  | `1`  | 最小值 1            |
| `page_size` | 否  | `20` | 1 到 100          |
| `email`     | 否  | -    | 邮箱模糊匹配，最大 254 字符 |
| `role`      | 否  | -    | `admin` 或 `user` |
| `active`    | 否  | -    | `true` 或 `false` |

没有 `online` 查询参数，不能按在线状态筛选。成功返回 `PageResponse<User>`，按 `created_at` 倒序：

```json
{
  "code": 0,
  "message": "success",
  "success": true,
  "data": {
    "data": [
      {
        "id": "<uuid>",
        "email": "user@example.com",
        "remark": "Example User",
        "role": "user",
        "active": true,
        "online": true,
        "created_at": "2026-09-14T12:00:00Z",
        "updated_at": "2026-09-14T12:00:00Z"
      }
    ],
    "total": 1,
    "page": 1,
    "pageSize": 20
  }
}
```

`online` 按本页用户批量查询 Redis。有未过期会话为 `true`，否则为 `false`。查询 Redis 失败返回 `503 SERVICE_UNAVAILABLE`，不要把整页渲染成离线。

前端建议：

- 用 `online` 显示在线标记；`active: false` 且 `online: false` 是已停用账号
- 踢下线成功后把该行 `online` 改为 `false`，或重新拉列表
- 不要把 `online` 当成 IM 心跳；用户关页但未退出时仍可能为 `true`

### 6.2 创建用户

```http
POST /api/v1/users
Authorization: Bearer <access_token>
Content-Type: application/json
```

```json
{
  "email": "user@example.com",
  "remark": "Example User",
  "password": "password123",
  "role": "user",
  "active": true
}
```

- `email`：必填、合法邮箱、最大 254 字符，保存为小写
- `remark`：必填、最大 100 字符
- `password`：必填，8 到 72 字节
- `role`：必填，`admin` 或 `user`
- `active`：可选，省略时默认为 `true`

成功返回 `201 Created` 和 `ApiResponse<User>`，其中 `online` 为 `false`。邮箱已存在返回 `409 CONFLICT`。

### 6.3 用户详情

```http
GET /api/v1/users/:id
Authorization: Bearer <access_token>
```

路径 `id` 为用户主键字符串，不校验具体格式。成功返回 `ApiResponse<User>`，含真实 `online`。不存在返回 `404 NOT_FOUND`。查询 Redis 失败返回 `503 SERVICE_UNAVAILABLE`。

```json
{
  "code": 0,
  "message": "success",
  "success": true,
  "data": {
    "id": "<uuid>",
    "email": "user@example.com",
    "remark": "Example User",
    "role": "user",
    "active": true,
    "online": false,
    "created_at": "2026-09-14T12:00:00Z",
    "updated_at": "2026-09-14T12:00:00Z"
  }
}
```

### 6.4 修改用户

```http
PATCH /api/v1/users/:id
Authorization: Bearer <access_token>
Content-Type: application/json
```

字段全部可选，但至少传一个：

```json
{
  "email": "new@example.com",
  "remark": "New Name",
  "password": "newPassword123",
  "role": "admin"
}
```

激活状态不能通过本接口修改，请使用状态接口。成功后目标用户的所有现有登录立即失效，返回的 `User.online` 为 `false`。

### 6.5 删除用户

```http
DELETE /api/v1/users/:id
Authorization: Bearer <access_token>
```

当前为物理删除，并会先让目标用户全部登录失效。不能删除当前登录的管理员自己。

```json
{
  "code": 0,
  "message": "user deleted",
  "success": true,
  "data": null
}
```

### 6.6 启用或禁用用户

```http
PATCH /api/v1/users/:id/status
Authorization: Bearer <access_token>
Content-Type: application/json
```

```json
{
  "active": false
}
```

成功返回 `ApiResponse<User>`。无论启用还是禁用，目标用户的全部现有登录都会失效，返回的 `online` 为 `false`。不能对当前登录的管理员自己执行该操作。

### 6.7 踢用户下线

```http
POST /api/v1/users/:id/kick
Authorization: Bearer <access_token>
```

只删除目标用户的 Redis Session，不修改 PostgreSQL 用户数据。该用户所有设备上的 Access Token 和 Refresh Token 都会立即失效。本接口不返回 `User`；之后再拉列表或详情时 `online` 为 `false`。

```json
{
  "code": 0,
  "message": "user sessions invalidated",
  "success": true,
  "data": null
}
```

## 7. HTTP 状态和错误码

| HTTP 状态 | `reason`              | 说明                       |
|--------:|-----------------------|--------------------------|
|     400 | `INVALID_REQUEST`     | 参数不合法                    |
|     400 | `INVALID_CAPTCHA`     | 验证码错误、过期或已使用           |
|     401 | `INVALID_CREDENTIALS` | 账号或密码错误                  |
|     401 | `UNAUTHORIZED`        | 未认证，或 Token / Session 无效 |
|     403 | `FORBIDDEN`           | 无权限，或请求 Origin 不被允许      |
|     404 | `NOT_FOUND`           | 资源不存在                    |
|     404 | `ROUTE_NOT_FOUND`     | 路径不存在                    |
|     405 | `METHOD_NOT_ALLOWED`  | 方法不允许                    |
|     409 | `CONFLICT`            | 通常表示邮箱已存在                |
|     413 | `PAYLOAD_TOO_LARGE`   | 请求体过大                    |
|     429 | `TOO_MANY_REQUESTS`   | 验证码拉取过于频繁                |
|     503 | `SERVICE_UNAVAILABLE` | PostgreSQL 或 Redis 暂不可用  |
|     500 | `INTERNAL_ERROR`      | 服务内部错误，响应中不包含原始原因        |

响应头 `X-Request-ID` 已通过 CORS `Access-Control-Expose-Headers` 暴露，可与服务日志关联。不要在客户端日志中记录 Access Token、Refresh Cookie 或密码。

## 8. CORS 与 Cookie

后端按完整 Origin 精确匹配白名单，包括协议、域名和端口。CORS 允许的方法：

```text
GET, POST, PATCH, DELETE, OPTIONS
```

Refresh 和 Logout 还会单独检查 `Origin`，防止第三方网页借助浏览器自动携带 Cookie 发起请求。获取验证码不需要 Cookie；登录、刷新、退出必须 `credentials: "include"`，否则浏览器不会读写 Refresh Cookie。

默认 Refresh Cookie：

```text
Name: springhere_refresh
Path: /api/v1/auth
HttpOnly: true
SameSite: Lax
Secure: false（仅本地开发）
```
